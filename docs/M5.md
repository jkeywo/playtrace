# M5 — approval and durable learning

M5 closes the gap between a reviewed recommendation and a traceable design
change. It does not make Play Trace an autonomous editor: a human approval is a
necessary gate, approval is not application, and generated code remains inert.

## Proposal lifecycle

`DesignProposal` binds a `ChangeSet`, its revision-guarded `SemanticPatchSet`,
postconditions, referenced behavioral regressions, and the complete review
basis. `basis_digest` hashes the embedded snapshot plus the full evidence and
policy records—not just their IDs. SQLite retains every transition and
application attempt as append-only history.

```text
draft -> pending -> approved -> applied
                  |           -> write_failed
                  |           -> validation_failed
                  +-> rejected
                  +-> revise -> pending
```

Only the `ProposalOrchestrator` may apply a proposal. It:

1. requires the exact approved state and basis digest;
2. compares the live snapshot with the approved snapshot;
3. runs revision/value preflight without writing;
4. returns immediately for a dry-run;
5. performs the bounded semantic patches;
6. rebuilds the snapshot through an injected adapter callback;
7. evaluates every required postcondition and referenced regression; and
8. records `applied`, `write_failed`, or `validation_failed` honestly.

Fixture gateways are deliberately dry-run only. `apply-proposal` requires the
live writable Google Workspace gateway, so a replay capture can never produce
an `applied` record or make a proposal eligible for promotion. Approval-state,
approval-digest, and current-snapshot mismatches are recorded as append-only
`preflight_failed` attempts and persisted by the CLI; they are not discarded as
exceptions before an audit fact exists.

The existing patch executor writes sequentially. A provider failure can
therefore leave partial writes; M5 records that possibility instead of claiming
rollback. Compensating transactions and Drive recovery are M6 work.

## Durable learning

`BehavioralRegressionCase` records a deterministic simulation configuration,
expected status, blocker IDs, event counts, selected metrics/state, its approval
origin, and the snapshot on which the expectation was established. Accepted
behavior and adversarial cases use the same game-neutral runner. Run digests
exclude observation clocks, so identical behavior has an identical digest.
Rejected or merely proposed cases cannot enter a suite.

Normal case construction is `proposed`. `accept-regression-case` is the explicit
decision path. An approved-behavior case must be linked to a successful,
non-dry-run application attempt from a proposal loaded from the same SQLite
store; a `source_proposal_id` string alone grants nothing. Adversarial cases do
not claim a proposal origin, but require nonblank design and acceptance
rationales. `run-regressions` requires the store and re-verifies accepted case
origins before either execution or persistence.

An applied proposal can be promoted explicitly with `promote-precedent`. The
result is an accepted `PrecedentCase` written only beneath that game's
`design/cases/` directory and linked back through `source_proposal_id`. Approval
alone is insufficient.

## Generated extensions

`GeneratedExtensionProposal` stores proposed simulation-plugin, CNL grammar, or
RuleIR source and proposed tests. Its content digest excludes lifecycle state
and append-only review history, allowing the explicit
`proposed -> pending -> approved/rejected/revise` workflow without changing the
generated content. Storage revalidates both the digest and history. The record
deliberately exposes no load, compile, register, or apply operation. Approval
means “approved for ordinary implementation review,” never dynamic execution.

## CLI surface

- `propose`, `submit-proposal`, `decide-proposal`
- `dry-run-proposal`, `apply-proposal`
- `promote-precedent`
- `accept-regression-case`, `run-regressions`
- `propose-extension`, `submit-extension`, `decide-extension`

The review shell displays linked proposals, regression runs, and extension
proposals read-only. Canonical writes still occur only through the explicit
apply command.
