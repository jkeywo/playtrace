# M4 — tabletop compiler and semantic strictness

M4 makes the executable boundary inspectable. It does not claim that arbitrary
rules prose is executable, and it does not turn Crisis Wardens' provisional
rulings into canonical rules.

## Delivered

### Narrow CNL → RuleIR → execution path

`TabletopRuleCompiler` parses controlled language into typed `RuleIR`.
`ExactRuleExecutor` executes the deliberately narrow exact subset:

- `IMPROVE "card-id"` removes one cube;
- `WORSEN "card-id"` adds one cube;
- `TRANSFER n "cube" FROM "source-id" TO "target-id"` moves the exact amount.

Targets must be IDs currently in the tableau. Phrases such as `"one Hazard"`
are selectors. They stop with an `ambiguous_source_rule` blocker unless the
game supplies an explicit `TargetSelector`, which must resolve to exactly one
legal target. Invalid amounts, empty Improve targets, unsupported resources,
and unsupported RuleIR kinds also produce typed blockers.

The Crisis Wardens runtime uses the shared exact state-change primitive for
Improve and Worsen, then applies registered game-specific events, assists,
affinities, and threshold interrupts around it.

### Plugin registry

The CLI and isolated worker resolve plugins through `SimulationPluginRegistry`;
neither imports nor switches on Crisis Wardens. Bundled plugins register their
project IDs, and installed packages may expose classes through the
`playtrace.simulation_plugins` entry-point group. Duplicate IDs and conflicting
project ownership fail during registration.

### Semantic audit

Each new `SimulationRun` includes a `SemanticAudit`:

| Origin | Meaning | Strict mode |
| --- | --- | --- |
| `compiled` | CNL compiled to typed RuleIR | allowed |
| `plugin_extension` | named, versioned game or subsystem code | allowed |
| `provisional_override` | registry-classified temporary ruleset or experiment | blocked |
| `missing_ambiguous` | execution gap or unresolved meaning | blocked |

Crisis Wardens inventories the shared cube primitive, scenario flow, threshold
behaviour, responder loop, provisional ruleset, registered overrides, compiled
snapshot rules, and blockers with entity/rule IDs and provenance. Its explicit
override registry owns each key's origin; unknown keys are invalid even when a
caller marks them canonical. Override execution counts reflect only the events
that actually consumed the override.

A `compiled_rule` kind is not sufficient by itself. The entity's `attributes.ir`
must validate as `RuleIR`, its ID must equal the entity ID, and a `compiles_to`
assertion must contain the identical typed record. Only a matching assertion supplies
compiled provenance. Missing, malformed, or contradictory records are classified as
`missing_ambiguous` and therefore block strict execution.

Set `"strict_semantics": true` in `SimulationConfig` to fail preflight when a
provisional ruleset or registered provisional override is declared. Runtime gaps still
stop as typed blockers. This field defaults to `false`, and the audit on saved
runs defaults to `null`, preserving M3 config and evidence JSON compatibility.

### Deterministic scripted policy

`ScriptedPolicyStep` describes one exact turn/actor action:

```json
{
  "turn": 1,
  "actor_id": "CHR-001",
  "action": "activate_card",
  "card_id": "CCD-O03"
}
```

`activate_card`, `rest`, and `pass` are typed. `ScriptedPlayerPolicy` consumes a
step only when it exactly matches a legal step exposed by the game runtime. A
missing, out-of-order, wrong-actor, or illegal step blocks and requests the
exact next step. It never falls back to greedy, random, or passive play.

### Strict bounded JSON input contract

`SimulationOverride.value` accepts JSON-compatible data only. Nulls, booleans,
safe integers, finite floats, valid Unicode strings, arrays, and string-keyed objects
are checked recursively under explicit depth, node, and exact encoded-byte budgets.
Depth counts containers on a path: a root array or object is depth one, while a
standalone scalar is depth zero. A limit of `N` therefore accepts exactly `N` nested
containers and rejects `N + 1` at the in-memory, raw-file, Docker-payload, and worker
boundaries.
Unsupported Python objects, sets, custom mappings, cycles, invalid Unicode, and
excessive values fail model construction with a structured Pydantic validation error;
they are not converted into simulation blockers or provenance markers. Validation
uses exact built-in type checks and never asks rejected objects for metadata or a
representation.

This separates transport validity from game meaning. A syntactically valid JSON
override such as an unknown target name reaches the Crisis Wardens plugin and returns
a typed `invalid_configuration` blocker. Malformed or out-of-contract input never
starts a run.

Simulation configuration files and isolated-worker requests pass through a bounded
JSON loader before Pydantic validation. File bytes are capped before reading; nesting
and node count are scanned before recursive decoding; long integer tokens are rejected
before integer allocation; and Unicode, finite-number, and compact encoded-size limits
are enforced consistently. Public Python callers use the normal `SimulationConfig`
constructor or `model_validate`, which return structured validation errors for invalid
values. Runners enforce the top-level `SimulationConfig` type; Docker payload creation
also applies the worker's aggregate byte, depth, and node budgets before serialization.

Pydantic's validation-bypassing `model_construct()` API, including arbitrary nested
graphs created through it, is explicitly trusted-internal and outside the public
simulation runner contract. Runners do not promise to revalidate or sanitize such
objects. CLI and worker inputs cannot invoke this API: they always cross the bounded
raw-JSON boundary and then `SimulationConfig.model_validate`.

## Verification

Tests cover compiler-to-executor mutation and transfer, selector blocking,
plugin resolution, strict audit classifications, exact scripted replay, illegal
scripts without fallback, strict rejection of provisional Crisis Wardens, structured
override validation failures, bounded raw JSON input, semantic blockers for valid JSON,
top-level runner type rejection, and worker/Docker bounded payload handling. Audit
tests distinguish explicitly consumed setup overrides from absent defaults and values
blocked before setup.
The full tests, bytecode compilation, JavaScript check, and whitespace diff
check form the release gate.
