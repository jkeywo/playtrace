# M3 — Evidence loop

M3 connects deterministic experiments to design reasoning without granting an
experiment authority over the game. A simulation, tension batch, or paired A/B
comparison can now become a typed, persisted evidence record linked to the
specific hypothesis it tests.

## Lifecycle

```text
Hypothesis
  → reproducible experiment artifact
  → explicit supports / contradicts / context / judgment link
  → dependency applicability check
  → evidence claim in the design review
  → pending / accepted / rejected / revise human decision
```

The relation is chosen by the recorder. Play Trace does not infer “supports”
from a good score, because a result only has meaning against the hypothesis's
declared outcomes and the designer's interpretation.

`ExperimentEvidence` preserves:

- the linked hypothesis and relation;
- observations and explicit assumptions;
- artifact, snapshot, configuration, plugin, runner, and ruleset provenance
  when the source artifact contains it;
- dependency revision/digest fingerprints;
- current or stale applicability with deterministic reasons.

Simulation evidence remains separate from `ExperientialEvidence`. A generated
trace is not an observation of players and cannot be presented as one.

## Recording an experiment

```powershell
uv run playtrace record-experiment C:\AnalogueGames\crisiswardens `
  --snapshot C:\AnalogueGames\crisiswardens\.playtrace\snapshot.json `
  --hypothesis C:\AnalogueGames\crisiswardens\design\hypotheses\tension.json `
  --comparison C:\AnalogueGames\crisiswardens\.playtrace\tension-comparison.json `
  --baseline C:\AnalogueGames\crisiswardens\.playtrace\tension-baseline.json `
  --candidate C:\AnalogueGames\crisiswardens\.playtrace\tension-candidate.json `
  --relation judgment `
  --rationale "The measured difference is too small to justify the candidate." `
  --assumption "The scripted policies approximate intentional play."
```

Use `--simulation` for a `SimulationRun` or `--batch` for a `TensionBatch`.
The output is an `ExperimentEvidenceBundle` containing the hypothesis, evidence
record, and generated claim. The same three records are stored in SQLite.

Include one or more bundles in a review with `assess --experiment-evidence
experiment-evidence.json`, then record the designer's review decision:

```powershell
uv run playtrace decide-review `
  --db C:\AnalogueGames\crisiswardens\.playtrace\playtrace.db `
  --review-id crisis-wardens:review:CURRENT_DIGEST `
  --state revise `
  --rationale "Retest with an observed player policy." `
  --decided-by "designer"
```

## Applicability and staleness

Evidence records the snapshot semantic digest and every source revision/digest.
At review time Play Trace constructs the same dependency map from the current
snapshot and compares it to the recorded map:

- an equal revision and digest is current;
- a changed revision or digest is stale;
- a missing required dependency is stale;
- optional runtime dependencies are checked when a current fingerprint is
  supplied, but their absence does not make all historical evidence stale.

Stale evidence remains visible, including its original relation and rationale,
but it does not satisfy current-evidence coverage. It can still be useful
context for deciding what to retest.

## Authority boundary

Evidence informs; acceptance does not mutate canon.

Recording evidence writes only disposable Play Trace state. Accepting,
rejecting, or requesting revision replaces the stored review decision. It does
not change the `Hypothesis.status`, create or approve a `ChangeSet`, call a
Workspace writer, or edit game-owned source files. Applying a proposed design
change remains a later, separately authorized workflow.
