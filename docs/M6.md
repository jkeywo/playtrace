# M6 — local-first production hardening

M6 makes the existing tabletop workflow safer to operate on one designer's
machine. It deliberately does not add video-game ingestion, hosting, accounts,
or multi-user coordination.

## Database lifecycle

SQLite state now has explicit transactional migrations and a schema version.
Opening a version-zero database adopts both an empty database and an existing
pre-M6 database using idempotent schema statements. Each version is committed
as a unit. A database created by a newer Play Trace build is refused rather
than opened optimistically.

```powershell
uv run playtrace migrate --db .playtrace/playtrace.db
uv run playtrace doctor --db .playtrace/playtrace.db --root .
```

The working database remains rebuildable state. Migration protects workflow
history and recovery journals while it exists; it does not make SQLite the
canonical home of game design.

## Workspace synchronization

`playtrace sync` fetches provider file metadata on every synchronization. A
source payload is reused only when the freshly observed provider version is
already in the revision-keyed cache. The structured project cursor records both
the Drive page token and the complete manifest mapping of file IDs to
last-observed versions. For Google Drive, a start-page token is
captured before the full refresh and every later Changes page is consumed before
the cursor advances, preventing an interrupted sync from skipping a page.
Optional `--app-property KEY=VALUE` checks
let a project verify Drive `appProperties`; cached metadata is never accepted
as authority for that check.

```powershell
uv run playtrace sync C:\AnalogueGames\crisiswardens `
  --access-token-env GOOGLE_ACCESS_TOKEN `
  --db C:\AnalogueGames\crisiswardens\.playtrace\playtrace.db `
  --app-property playtraceProject=crisis-wardens
```

## Canonical write sagas

Live `apply-proposal` calls now journal an exact bounded before/after text image
and SHA-256 digest for every document operation (and a before-image for every
sheet operation),
write and verify one operation at a time, and record progress durably. Each
transport attempt is first recorded with an unknown outcome, then its returned
provider response and verification are separate journal transitions. `applied`
therefore means awaiting post-write validation; only `committed` is successful
and terminal. If a
later operation fails, completed operations are compensated in reverse order
and the restoration is verified. A completed write set is likewise compensated
if post-write validation or a referenced regression fails. The proposal's
`ApplicationAttempt` includes
the saga ID, exact failures, and whether operator recovery remains necessary.

All document coordinates are handled as Google Docs UTF-16 code units. This
includes preflight extraction, request extents, verification, journal images,
and inverse edits, so non-BMP characters cannot shift or split a patch range.
Multiple non-overlapping patches for one document and revision are sent as one
atomic `batchUpdate`, ordered from highest to lowest index within each tab, and
are journaled and compensated as one exact group. Overlapping ranges or mixed
required revisions are rejected before any write.

An interrupted or conflicted recovery is never described as rolled back. Retry
it explicitly after inspecting canon:

```powershell
uv run playtrace recover --saga-id PROPOSAL:ATTEMPT:saga `
  --db .playtrace/playtrace.db `
  --access-token-env GOOGLE_ACCESS_TOKEN
```

Compensation checks the exact expected after-layout before applying the inverse
edit, then verifies the exact before-image digest. Only an exact full
before-image match is treated as already restored; overlapping replacement and
context strings cannot be mistaken for recovery. If another editor has changed
a target after the failure, Play Trace refuses to overwrite their work and
keeps the saga in `recovery_failed`.

Legacy saga payloads that predate durable `attempted` and `write_outcome`
fields are migrated conservatively from their saga and operation state. Any
possibly attempted write is inspected against canon and either compensated,
recognized as already restored, or left in `recovery_failed`; it is never
skipped merely because the old field was absent. Discovery durably adopts the
canonical payload and status in one SQLite transaction, so `doctor`, recovery,
and the local review projection all report the same incomplete saga set.

## Typed critics

`ExecutorCriticPipeline` sends a schema-bearing task through ordered local,
subscription CLI, then API executors. Timeouts are enforced by the concrete
HTTP/CLI executors, HTTP bodies and live CLI stdout/stderr are bounded, and every failed and successful
attempt records executor/model provenance. Responses must validate as typed
`CriticFinding` records for the routed critic, return the requested task ID,
and reference only basis/claim IDs supplied in that task.

The HTTP executor transmits the requested JSON Schema in a versioned response
contract inside the chat message. This works with any chat-compatible endpoint
without binding Play Trace to a provider-specific structured-output extension.

Critics remain optional analysis. `MandatoryCoverageEngine` is deterministic
and independent of model success, so an executor outage cannot silently turn
missing mandatory material into covered material.

Use `playtrace run-critics` with one or more of `--local-command`,
`--cli-command`, or the paired `--api-endpoint`/`--api-model` options. Every
routed run is persisted for the unified review projector. API credentials are
read only from the environment named by `--api-key-env`. Metered fallback is
disabled unless `--allow-metered-api` and a positive `--api-call-budget` are
both supplied; an empty credential is rejected before any critic runs. Each
persisted attempt records whether it was metered and any scalar provider usage
fields. Repeated executions are distinct occurrences even when their stable
task digest is identical.

## Unified local service

`playtrace serve` projects reviews, evidence, proposals, regression results,
extension proposals, critic runs, and write sagas through one read-only local
API. It also provides bounded typed background jobs, progress events, and
cancellation. The dependency-free standard-library server was retained rather
than adding FastAPI: the current surface needs no framework features and this
keeps installation and the offline boundary small.

The server accepts explicit IPv4 loopback addresses only, preflights the
database read-only before binding, caps request bodies,
offers no arbitrary command endpoint, sends `no-store`/`nosniff` headers, and
exposes:

- `GET /api/health`
- `GET /api/review`
- `POST /api/jobs` with the `project-review` kind
- `GET /api/jobs/{id}` and `GET /api/jobs/{id}/events`
- `DELETE /api/jobs/{id}`

## Isolated simulation container

`container/Dockerfile` pins the Python base by digest, installs the exact
`uv.lock` as a non-editable package, proves that the copied runtime environment
can import both `playtrace` and its simulation worker without a source tree, and
runs as a non-root user. The runtime command already enforces a
networkless, read-only filesystem with memory, CPU, and PID limits. The checked
in image contract records the canonical LF Git-blob digest of the dependency
lock, so verification is stable across Linux and Windows checkouts.

```powershell
uv run playtrace container-doctor --root .
uv run playtrace container-doctor --root . --smoke `
  --image ghcr.io/OWNER/playtrace-simulation `
  --image-digest sha256:PINNED_DIGEST
```

The smoke check runs a bounded simulation request through the real read-only
input and writable result mounts, then validates the worker's result. The host
creates only those mount directories with explicit permissions suitable for the
container's unrelated non-root UID. Worker process output is discarded and
`result.json` is size-bounded and must be a regular, non-symlink file. The smoke
check is optional because the local design workflow and CI static contract checks
must remain useful when Docker Desktop is not installed or running.
