# M2 — taste and evidence system

Phase 2 turns design judgment into an inspectable argument. Deterministic code
selects mandatory material and checks coverage before any critic is trusted;
judgment remains permitted but must be labelled.

## Delivered

| Requirement | Implementation | Enforcement |
|---|---|---|
| Layered policy | Typed shared, game, and intent layers with severity and explicit override IDs | Applicability and override resolution happen before review assembly |
| Precedent cases and scoped retrieval | Cases retain alternatives, criteria, evidence, disagreement, decision, consequences, and applicability | Only accepted cases are retrieved; order is same game, same medium/capability, general, then labelled cross-medium analogy |
| Hypothesis model | Hypotheses now include basis IDs and required evidence classes in addition to supporting and contradicting outcomes | Consequential deck-pacing advice becomes a test rather than an immediate change |
| Mandatory coverage | Hard policy, explicit intent-scope IDs, and current scoped experiential evidence become deterministic coverage targets | Every target records which claim, hypothesis, or finding examined it; missing targets fail completeness |
| Experiential evidence | Typed observations separate source revision, location, observer, assumptions, dependencies, applicability, and designer evaluation | Authored rules cannot be silently reclassified as play experience |
| Critic routing | Three core critics always run; specialist critics are selected from the bounded intent scope | Routing reasons are visible and critic disagreement is preserved without averaging |
| Claim-linked UI | The browser review shows intent, coverage, policy, claims and their evidence links, hypotheses, critic findings, routing, alternatives, and limitations | Unsupported findings carry a visible `UNSUPPORTED JUDGMENT` label |

Policy, cases, evidence, reviews, and claims are persisted in SQLite and indexed
through FTS5. Shared policy lives in this repository; game-specific knowledge
lives with the game it judges.

`C:\AnalogueGames\crisiswardens\design\intent\first-playable-scenario.json`.
It does not edit Drive.

- the mandatory core and eight relevant specialist critics are routed with
  recorded reasons;
- all 16 mandatory coverage targets are explicitly examined;

  fabricated;
- the intended-player-experience finding is visibly labelled unsupported
  judgment.

The review is written to
`C:\AnalogueGames\crisiswardens\.playtrace\phase2-review.json` and stored in its
SQLite working database. The browser-rendered surface was checked for the
expected claims, coverage state, critic routes, visible judgment label,
horizontal overflow, and console errors.

## What this enables now

Play Trace can make bounded, source-linked diagnoses of Crisis Wardens and turn
consequential conclusions into hypotheses with explicit evidence needs. It can
identify concrete contradictions such as the deck-size mismatch and distinguish
those from claims about fun or feel that still require play.

It still cannot execute a game turn. That belongs to the later play-trace and
simulation phases; Phase 2 establishes the policy/evidence discipline those
results will enter.
